# PollyOS 目录、存储与 Linux 兼容设计

> 日期：2026-10-07。状态：已确认的目标设计，尚未完成迁移及运行验收。
> 本文作为后续安装、账户、应用管理、系统维护和救援改进的共同依据。
> 不改变现有 Live/D1 产物，不代表授权真实磁盘写入、生产密钥操作或发布。
> 当前实施优先级：**P0，先于其余功能扩展**。任务、依赖和进度只在执行台账维护；
> 本文维护技术契约，不以增加文档篇幅代替实现或验收。

配套入口：[技术简介与交接](POLLYOS.md)、[执行台账](POLLYOS-BACKLOG.md)、
[当前应用包机制](../desktop/APPLICATIONS.md)。

## 1. 核心决策

1. 主系统采用普通、可写的 ext4 根文件系统，不要求只读，不以 `Rootfs.img`
   作为主系统默认运行载体。
2. 后续新安装目标采用单主系统加独立救援，不要求固定 A/B 系统分区。
   更新失败后允许进入救援修复或重装，不承诺立即启动旧版本。
3. 程序资源、系统状态、共享应用、用户内容和救援载荷分层分责，
   产品入口为 `System`、`SystemData`、`Apps`、`Users`、`Recovery`。
4. 系统软件树实际存放在 `/System/Resources`；Linux 继续通过 `/usr` 访问
   同一份内容。不为命名重新拆分 Debian 包，也不复制两份系统程序。
5. apt/dpkg 管发行版软件，Polly 应用管理器管独立应用包；二者不共同管理
   同一份程序或维护两份权威安装记录。
6. 用户 App 程序包默认全机共享，安装注册全局管理；个人设置、AppData、
   文档和缓存按稳定用户身份隔离。
7. 系统状态属于数据，但恢复规则不同：密码和身份保持最新，包数据库必须
   与恢复后的系统软件匹配。目录归类不能代替更新事务。

`Resources` 在本文中表示系统软件资源，包括可执行程序、库、模块、资源和文档，
不是仅表示图片、字体，也不是用户共享文件。
不再使用 `Software`、`Runtime`、`Programs` 等额外产品层名称。

## 2. 命名规则

- 产品自定义目录使用首字母大写的完整名称；多词采用 PascalCase，
  不使用连字符或下划线。
- 区域、功能、整体用单数，例如 `System`、`Library`、`Boot`、`Recovery`、
  `Cache`；对象集合用复数，例如 `Resources`、`Apps`、`Users`、`Accounts`、
  `Packages`、`Settings`、`Logs`。`Data` 作为整体概念不加 `s`。
- Linux 兼容路径、发行版内部目录、软件包文件名和应用 ID 保持原样，
  不因产品命名规则重命名。所有路径区分大小写。
- `<UserId>` 表示稳定数值 UID，不是显示名；改用户名不能改变数据身份。
  系统服务账户与人类账户须避免 UID/GID 冲突。
- `<PackageHash>` 沿用应用包内容摘要语义，包含文件路径、内容和可执行标记；
  不能以版本字符串替代内容身份。

## 3. 目标目录

```text
/
├─ System/                              主系统文件
│  ├─ Resources/                        原 /usr 的完整内容，实际存储
│  │  ├─ bin/
│  │  ├─ sbin/
│  │  ├─ lib/
│  │  ├─ share/
│  │  └─ …                              保留发行版其他目录及文件名
│  └─ Boot/                             发行版内核、initramfs 和启动配套文件
│
├─ SystemData/                          本机持久状态
│  ├─ Library/                          系统服务支持数据
│  │  ├─ Dpkg/                          Debian 包数据库
│  │  ├─ Apt/                           apt 状态
│  │  └─ <ServiceName>/                 经分类的其他服务数据
│  ├─ Accounts/                         账户、密码哈希、角色、认证状态
│  ├─ Apps/
│  │  ├─ Registry/                      Polly App 全机安装与版本记录
│  │  └─ Permissions/                   Polly App 系统授权策略
│  ├─ Settings/                         受管理的本机服务配置
│  ├─ Machine/                          主机身份与设备配置
│  ├─ Network/                          网络配置与受保护凭据
│  ├─ Credentials/                      其他受保护的密钥和令牌
│  ├─ Setup/                            系统初始化流程记录
│  ├─ Updates/                          更新、迁移和恢复事务
│  ├─ Logs/                             持久系统日志
│  ├─ Cache/                            可重建的系统缓存
│  └─ Temporary/                        可跨重启保留的临时文件
│
├─ Apps/                                全机共享的 Polly App 程序
│  └─ Packages/
│     └─ <PackageHash>/                 完整程序包、资源及包清单
│
├─ Users/
│  └─ <UserId>/                         稳定账户身份对应的家目录
│     ├─ Documents/
│     ├─ Desktop/
│     ├─ Downloads/
│     ├─ Settings/                      个人设置
│     ├─ AppData/                       应用持久数据
│     ├─ AppState/                      应用历史及恢复状态
│     └─ Cache/                         可重建缓存
│
└─ Recovery/                            独立救援载荷
   ├─ Boot/
   │  ├─ Kernel
   │  └─ Initramfs
   ├─ Rootfs.img                        仅救援系统使用的镜像
   └─ Manifest.json
```

这是产品存储结构，不是根目录下所有文件的穷举。`/etc`、`/var`、`/home`、
`/run`、`/tmp`、`/dev`、`/proc`、`/sys`、`/opt`、`/root`、`/mnt`、
`/media` 等标准入口仍存在。
不要求所有发行版文件只能物理存放在五个产品目录中。

`/System/Resources` 保留完整 `/usr` 树，包括发行版实际提供的多架构库、
`libexec`、`local` 等内容；不能只复制图中列出的四个目录。
不再额外建立 `Resources -> /usr/share` 链接。

## 4. 分区与存储归属

推荐新安装布局：

| 区域 | 内容 | 边界 |
|---|---|---|
| EFI 分区 | 正常和救援启动入口 | 不自动修改宿主固件策略或 Secure Boot |
| 主系统分区 | Linux 根目录、`System`、版本相关兼容配置 | 可写 ext4，支持 apt 维护 |
| 持久存储分区 | `SystemData`、`Apps`、`Users` | 可在一个文件系统中分目录存放，不要求三个分区 |
| 救援分区 | `Recovery` 的内核、initramfs 和救援文件系统 | 主系统软件损坏时仍可独立读取、启动 |

容量根据载荷、更新暂存、应用及恢复材料实测确定，不沿用 D1 的固定槽容量
作为产品承诺。持久分区的后台挂载点是实现细节，不能成为应用使用的公开路径。

普通目录不是可启动系统。`Recovery` 必须具备不依赖主系统程序、库或账户加载
流程的启动链。救援可使用镜像，不意味着主系统也必须使用镜像。
共用 EFI 时，EFI 损坏仍需要外部恢复介质；本布局也不能恢复损坏磁盘本身。
可选加密另行实现，不因本设计默认开启。

## 5. Linux 路径映射

映射指向同一份存储，不复制两份内容。

| Linux 路径或接口 | 产品存储 | 接入要求 |
|---|---|---|
| `/usr` | `/System/Resources` | initramfs 中、启动主系统前完成绑定挂载 |
| `/usr/bin`、`/usr/sbin`、`/usr/lib`、`/usr/share` 等 | `Resources` 内原有子目录 | 随整个 `/usr` 接入，不逐个重新分类 |
| `/bin`、`/sbin`、`/lib`、`/lib64` 等 | Debian 提供的对应路径 | 保留发行版原有目录或链接关系 |
| `/boot` | `/System/Boot` | 提供兼容入口；引导程序按真实存储路径定位启动文件 |
| `/boot/efi` | EFI 分区 | 按需挂载，写入限定目标和操作范围 |
| `/var/lib/dpkg` | `/SystemData/Library/Dpkg` | 必需绑定挂载，保留 dpkg 预期权限与布局 |
| `/var/lib/apt` | `/SystemData/Library/Apt` | 必需绑定挂载，保留 apt 预期权限与布局 |
| 其他 `/var/lib/<服务>` | 经分类的 `Library/<ServiceName>` 或专用状态目录 | 逐服务确定，禁止整体映射 `/var/lib` |
| `/var/log` | `/SystemData/Logs` | 绑定挂载，保留轮转和访问控制 |
| `/var/cache` | `/SystemData/Cache` | 绑定挂载，可按规则清理重建 |
| `/var/tmp` | `/SystemData/Temporary` | 绑定挂载，保留标准权限及清理规则 |
| `/home/<用户名>` | `/Users/<UserId>` | 绑定挂载；用户名不是持久数据身份 |
| `/root` | `/Users/0` | 正常系统中的 root 持久家目录，严格限制访问 |
| 受管理账户认证 | `/SystemData/Accounts` | 受控挂载及 NSS/PAM 接入，不整体替换系统账户表 |
| 受管理本机配置 | `Settings`、`Machine`、`Network` 等 | 服务接口或逐项配置映射 |
| `/run`、`/tmp` | 临时文件系统 | 不进入持久数据 |
| `/dev`、`/proc`、`/sys` | 内核接口 | 标准挂载 |

`/boot` 的链接或挂载形式须在引导实施中验证；只让运行中的 Linux 能看到文件
不够，GRUB 在主系统挂载前也必须能读取对应内核、微码和 initramfs。
`update-initramfs`、`update-grub`、包安装脚本和重启链路需覆盖同一套真实路径。
不能用一条未经验证的链接宣布已支持内核升级。

### 5.1 `/etc` 的边界

`/etc` 保留为运行时配置入口，不整体映射到 `System` 或 `SystemData`。

- 软件包提供的配置文件及其 dpkg conffile 元数据，按 Debian 升级规则维护。
- 账户、主机身份、网络凭据等已有专门归属，不另复制到通用 `Settings`。
- 需要跨系统恢复保留的其他服务配置，在 `SystemData/Settings` 中按服务管理；
  每项必须定义权威来源、加载方式、权限、schema、升级和恢复规则。
- 直接链接或绑定配置前检查对应包的替换、原子写入和安装脚本行为；
  apt 不能静默覆盖持久配置接入，也不能产生两份同时可写的权威记录。
- 完整系统恢复须处理版本相关配置和持久覆盖的兼容性，不能只恢复 `/usr`。

### 5.2 用户目录与 XDG

普通用户登录时：

```text
HOME              = /home/<用户名>
XDG_CONFIG_HOME   = $HOME/Settings
XDG_DATA_HOME     = $HOME/AppData
XDG_STATE_HOME    = $HOME/AppState
XDG_CACHE_HOME    = $HOME/Cache
```

为传统路径提供兼容链接：

```text
~/.config         -> Settings
~/.local/share    -> AppData
~/.local/state    -> AppState
~/.cache          -> Cache
```

已有同名文件或目录先检查、迁移和校验，不能直接覆盖。
文档、桌面和下载位置通过 XDG 用户目录配置接入；`.profile` 等必要兼容文件
可以正常存在。不得以所有应用都遵循 XDG 为假设，特殊应用另做适配。
root 的 HOME 按对应账户配置提供，不强制设为 `/home/root`。

## 6. 启动顺序与失败行为

1. UEFI/GRUB 读取指定主系统版本的内核、微码和 initramfs。
2. initramfs 按已配置的设备身份挂载主系统，验证资源布局，
   将 `/System/Resources` 接入 `/usr` 后再启动主系统 init。
3. 按预期 UUID、文件系统和布局版本接入持久存储；建立产品入口、
   包数据库、服务数据和用户家目录的必需映射。
4. 校验账户存储、UID/GID、权限、认证初始化状态和包状态配套关系。
5. 必需状态就绪后才开放 apt 管理、正常登录及桌面会话。

早期挂载所需工具必须由 initramfs 自身提供，不能先调用尚未接入的 `/usr`。
不能只依赖普通开机服务建立 `/usr`，否则 merged-usr 的 init/动态加载器
可能在服务启动前就无法运行。

必需卷缺失、UUID 错误、布局不匹配、不可写、损坏或空间不足时，明确显示错误
并进入受控诊断/救援流程。禁止静默使用根分区里的空挂载目录继续保存数据，
也禁止创建空 dpkg 数据库、退回默认密码、无密码登录或重新开放初始化。
故障处理不得自动格式化、修复或扩大写入到未知磁盘。

## 7. apt、系统维护与恢复一致性

### 7.1 日常维护

apt 仍操作 `/usr`、`/etc`、`/var/lib/dpkg`、`/var/lib/apt`、`/boot` 等标准路径。
管理员可以写主系统，不宣传为 macOS 式签名只读系统卷。

apt 安装的桌面应用也属于发行版软件树，不会自动移到 `/Apps`。
Polly 不改写 `.deb` 的任意安装路径，也不是通用 `.deb` 转换工具。
`dpkg-divert`、配置升级、内核包脚本和包锁必须保留正常语义。

必要挂载检查完成前不得运行 apt。Polly 管理动作不得绕过 apt/dpkg 包锁；
离线恢复前须确保主系统不再写入，不能与活动 apt 事务并发。

### 7.2 恢复分组

| 状态 | 恢复规则 |
|---|---|
| 系统软件、内核/模块/initramfs、版本相关配置、Dpkg/Apt 状态 | 作为匹配的系统恢复组同步恢复或重建 |
| 账户密码、UID/GID、管理员策略、主机身份、初始化状态 | 保留最新权威记录；旧系统不能恢复旧密码或重新开放 setup |
| 网络和其他凭据、持久服务配置 | 保留最新兼容状态；不兼容迁移需备份、验证和明确拒绝策略 |
| Polly App 程序与全机注册 | 按应用事务恢复，不因更换系统隐式降级或卸载 |
| 用户文档、设置和 AppData | 默认不覆盖；数据迁移不能假定旧代码仍能读取 |
| 缓存和临时文件 | 可按明确规则重建或清理，不混同用户数据 |

`Library/Dpkg` 放在数据区不代表可以无条件保留最新数据库。
同样，目录在同一分区内也不自动获得事务一致性。

完整系统更新或恢复至少记录操作 ID、源/目标状态、恢复范围、校验结果、
当前阶段和失败信息，权威事务记录放在 `SystemData/Updates`。
写前准备恢复材料并验证来源、空间和兼容性；中断后识别未完成状态，
从救援环境明确继续、修复或恢复，不把半成品声明为成功。
恢复材料必须包含匹配状态，包名称列表不是完整系统备份。

本设计不选择在线自动升级、文件系统快照后端或自动旧版本回退。
不默认下载、执行未知恢复代码；正式载荷的签名信任根和生产密钥另行确认。
校验和只能检测内容变化，不代替来源认证。

## 8. 账户、权限与共享应用

### 8.1 系统状态

`Accounts` 保存密码哈希而非明文密码；沿用受控标准改密及 PAM/NSS 接入。
保留当前“缺失或损坏状态拒绝认证”的边界，不直接把整个 `/etc/passwd`
或 `/etc/shadow` 指向共享数据，避免丢失版本配套的服务账户。
UID/GID 及 shadow 访问组需显式协调，不能因重装漂移。

账户初始化完成状态只有一个权威来源；`Setup` 可以记录整体流程，但不得
与 `Accounts` 各维护一个互相矛盾的认证初始化开关。
密码、哈希、令牌和私钥不得进入普通日志、测试结果或发行镜像。

`SystemData` 由系统管理，但不能笼统给所有子目录同样权限。
包查询所需权限遵循发行版；账户、凭据和策略按最小必要访问配置。
命名、隐藏目录和权限不等于磁盘加密。

### 8.2 共享程序与全局注册

`Apps/Packages` 和 `SystemData/Apps/Registry` 由受限安装管理机制维护，
普通 App 运行时不能修改共享程序。包发布前暂存、校验和同步，
再原子更新注册；保留现有内容摘要、旧版本、失败反馈和稳定 app-id 规则。
用户数据不会随包位置、显示名或版本变化而改变身份。

全机安装、替换、卸载须有明确授权策略；后端验证真实调用者和操作范围，
不信任自报 UID，不提供任意 root 命令、路径写入或脚本执行。
复用当前包校验、归档限制和无安装脚本原则，不能直接把现有 `polly-app`
整体以 sudo/root 运行作为共享方案。

已确认：每个 app-id 只有一个全机活动版本。旧用户版本冲突由管理员显式选择，
保留各用户数据和旧版本；未完成选择前不得静默切换或按版本号自动选“最新”。

默认共享程序全机可用。`Permissions` 保存授权策略，但启动器检查本身不能
阻止用户直接执行可访问文件。若要求限制某用户使用某应用，还需相应文件权限、
ACL 或其他系统级强制机制；未实现前不得宣称已经提供应用执行隔离或沙箱。

全局卸载不同于隐藏个人入口；不能因为一个用户移除快捷方式就删除共享包。
回收前同时检查安装/保留版本引用与仍使用资源的进程，不只检查启动器主 PID。
清理用户数据是独立、明确授权的操作。

### 8.3 两种应用来源

| 内容 | Debian/apt | Polly 应用包 |
|---|---|---|
| 程序 | `System/Resources` 及包规定的其他标准位置 | `Apps/Packages` |
| 权威安装记录 | `SystemData/Library/Dpkg` | `SystemData/Apps/Registry` |
| 更新/卸载 | apt/dpkg | Polly 应用管理器 |
| 桌面入口 | 标准 `.desktop` | Polly 注册记录生成的入口 |
| 个人状态 | 当前用户 HOME/XDG，特殊应用另行适配 | 当前用户 XDG/Polly 存储接口 |

启动器统一展示来源并区分身份，不再为 apt 应用建第二份权威安装数据库。
不能把运行库声明视为所有 ABI/依赖均兼容的证明。

## 9. 独立救援

救援包含自己的内核、initramfs、文件系统和必要诊断/恢复工具，能在主系统
资源或包数据库损坏时启动。恢复来源可以是已验证本地材料、外部介质或
受信任下载来源；没有可用来源时明确报告不能恢复。

默认诊断不扩大写入。修复、重装、账户恢复和加密卷解锁分别有受控权限及
明确范围，不能因为进入救援就绕过账户策略或泄露其他用户数据。
具体恢复授权界面和可选加密交由 M10 实施，不内置默认密码或万能密钥。
救援更新不得与主系统更新一起破坏唯一可用的恢复入口。
已确认：诊断默认只读且不开放个人数据；修复、重装及账户恢复写入须认证
`polly` 管理员或 root。忘记全部密码时不提供内置密码重置入口，不生成默认恢复码，
也不因账户状态缺失而开放 root shell。

## 10. 当前实现与差距

| 当前实现 | 目标差距 |
|---|---|
| `desktop/tools/build-installed-image.py` 生成 ext4 A/B 加独立 `/home` | 新单系统/持久存储/救援布局、真实路径与独立启动链尚未实现 |
| `desktop/release/install/accounts.py` 使用 `/home/.polly-system/accounts` | 需迁移到 `SystemData/Accounts`，更新 UUID、挂载和权限校验 |
| `passwd-proxy.c`、PAM/NSS 使用当前账户兼容路径 | 必须一起适配，保持标准改密及拒绝绕过行为 |
| 安装会话固定 `/home/polly`，现有 XDG 数据与命名空间已使用 | 需按稳定 UID 接入 HOME/XDG，保留数据身份并验证兼容链接 |
| `polly-app` 是普通用户私有对象库与注册，详见应用文档 | 共享库和全局注册需新的受限管理边界，不是路径替换 |
| 当前启动配置和证据使用 A/A/B/A | 只能作为历史回归，不能作为新单系统、apt 或救援验收 |

本文变更不搬动现有数据、删除旧对象或重建已有镜像。
当前产物和历史证据继续按原布局解释，直到新候选独立验收。

## 11. 执行入口与迁移准入

依[执行台账第 16 节](POLLYOS-BACKLOG.md#16-完整执行清单与依赖)的 P0 顺序推进：
布局/早期启动 → 身份与用户数据迁移 → 共享应用、apt/内核维护 → 独立救援与
一致恢复；软件闭环后才进入授权的真实外置安装。沿用 M01/M04/M06/M07/
M09/M10/M15 的稳定任务 ID，不在本文维护第二套进度或以编号推导额外依赖。

共享代码可按内容去重，但多个旧用户对同一 app-id 的不同活动版本不能默默
选一个。冲突规则在迁移前明确；未解决时保留原数据并阻止切换。
迁移具有格式版本、暂存、校验、提交和中断记录；验证前保留源，不以清空
或重新初始化替代迁移。清除旧状态和物理回收另行确认。

## 12. 验收矩阵

| 范围 | 最低验收 |
|---|---|
| 路径一致性 | `/usr` 与 `System/Resources` 访问相同内容，标准链接和完整软件树保留 |
| 正常启动 | 正常候选无 fixture 冷启动，早期挂载、PAM/logind 和桌面顺序正确 |
| 必需状态故障 | 缺卷、错 UUID、坏 schema/权限、不可写、满盘和中断均明确拒绝，不落入空目录 |
| apt | 安装、升级、卸载、包查询、配置冲突、锁竞争及中断修复；数据库与软件匹配 |
| 内核 | 内核与模块匹配，微码、initramfs、GRUB 更新后实际冷启动成功 |
| 账户 | 登录/改密/su/重启/恢复后新密码有效、旧密码失效，初始化不重开，身份不漂移 |
| 用户隔离 | 至少两个测试用户共享代码但不混合 HOME、设置、AppData、缓存；root HOME 也持久 |
| 应用 | 安装/替换/退役/恢复/并发/篡改检测，权限拒绝，使用中代码不误删 |
| 数据迁移 | 现有设置、managed app 数据、文档保留；未知数据不自动收养，冲突和 schema 变化明确处理 |
| 救援 | 主系统资源或包状态损坏时仍可启动；无恢复材料明确失败，不触碰无关磁盘 |
| 恢复一致性 | 系统、启动文件、配置与包状态配套；最新密码、凭据和用户内容不被旧系统覆盖 |
| 更新中断 | 在暂存、写入、状态提交及引导更新等关键阶段中断，重启后可诊断并明确恢复 |

每项记录实际版本、硬件/虚拟环境、操作范围、失败产物和结论。
普通软件回归、VM 冷启动、异常断电和真实介质验收分别报告，不互相替代。
