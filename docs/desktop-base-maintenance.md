# PollyDesktop 底座选择与维护同步计划

决策日期：2026-10-06。

**已确认的方向：Debian 13「trixie」amd64 最小基础系统，
通过 `debootstrap --variant=minbase` 生成 rootfs，再组装自己的系统镜像。**
本文件是后续底座与维护工作的依据，不表示 Debian 移植、软件源、
持续集成、定时同步或更新服务已经实现。

实施进展：用户已批准 A1–A8 迁移任务。`debootstrap minbase` 构建和基础校验
已经落地；应用、服务及启动介质的等功能验收仍在进行。
实际入口与状态见 [Debian 构建说明](../desktop/release/debian/README.md)。
这不代表已建立新的实机验收基线或自动同步服务。

## 1. 当前基线与目标

第一阶段是实体机基础功能验证，不是构建大而全的桌面发行版。
用户已报告 Alpine alpha.4 在选定机器上验证通过。现有源码基线为
`4ae38ed`；启动介质、目标机器及限制见
[Live 镜像说明](../desktop/LIVE.md)。
这是用户反馈的首台机器验收，不等于逐张 GPU、所有接线组合或广泛硬件矩阵
都经过了独立测量。

Alpine 镜像保留为可退回的已验证基线。Debian 必须重新通过等功能的
构建、运行与实机验收，不能继承 Alpine 的测试结论。
迁移期间不删除可工作的 Alpine 路径；Debian 基线通过后，不默认承担
两个发行版长期平行扩展的维护负担。归档版本必须明确标为历史版本，
不能继续暗示其获得安全维护。

第二阶段的目标是能反复使用、保留数据并在失败时恢复的小型实机开发系统。
持久化和升级布局应在 Debian 启动基线建立后定型。
文件管理器、完整 Portal/录屏、完整无障碍、高级效果、Xwayland、
其它架构和平台不因换底座自动成为本阶段任务。

## 2. 从最小集合向上构建

| 名称 | 定位 | 本项目的选择 |
|---|---|---|
| Debian `minbase` rootfs | 由官方软件包组成的最小用户空间，不是预装桌面的 SKU | 系统底座 |
| `debian:trixie-slim` | 容器基础镜像，不包含完整实机启动链路 | 可作为构建/CI 环境；不能直接冒充 Live 系统 |
| Debian netinst | 可选择安装内容的网络安装介质 | 可供手工实验；不是发布镜像的构建起点 |
| Debian KDE/GNOME Live | 已集成其它桌面的完整启动镜像 | 不采用，不走“先装再拆”路线 |

在最小 rootfs 上明确增加内核、目标驱动/固件、启动与设备服务、
必要的登录/网络/音频组件、图形运行库、字体/输入法，以及
PollyWM + PollyShell + PollyUI。`minbase` 本身并不是可启动桌面。

不安装整套桌面任务包，不盲目安装推荐包。每个新增运行包必须能解释：
哪个已承诺的功能依赖它、为何需要它、对体积/权限/许可证有何影响。
关闭推荐包安装时也必须显式补齐实际必需的运行依赖，不能靠开发镜像掩盖缺包。
编译器、头文件和 SDK 不进入运行镜像；Mesa 等确实需要的 LLVM 运行库
不能仅因名字类似开发工具就删除。

继续保持独立桌面边界：

- PollyWM 是自己的 wlroots 合成器，不改为 labwc、GNOME 或 KDE。
- PollyUI 引擎不依赖桌面；PollyWM 不引入整个 JS/UI 引擎。
- 自有运行时/服务不引入 GLib/GIO/GObject 的约束仍有效。
  独立第三方软件的依赖另行记录，换成 Debian 不构成约束例外。
- 不为兼容性默认增加特权代理、polkit 或应用沙箱；需要这些能力时单独说明。
- 本决策没有自动批准 init/login 服务替换。Debian 的服务配置、PAM、
  seat 和 login1 接口需要在移植时明确接通，不能直接照搬 OpenRC 配置。
- 无密码 Live、默认禁用密码锁，以及暂缓电源授权/挂起/休眠的现有决定不变。

## 3. Debian 版本与软件源

初始参考点为 Debian **13.7**，这是决策日官方公布的稳定点版本。
实际生成的 rootfs 还会包含之后发布的更新，必须以构建清单中的包版本为准，
不能只用“13.7”代替完整的软件物料记录。

| 来源 | 使用策略 |
|---|---|
| `trixie` | 常规基础包 |
| `trixie-updates` | Debian 稳定版更新 |
| `trixie-security` | 安全更新 |
| `trixie-backports` | 仅为具体硬件/功能按包选择；记录连带依赖，不整体切换 |
| testing / sid | 不混入正式构建的软件源 |

软件源固定写代号 `trixie`，不使用会随 Debian 大版本变化的 `stable` 别名。
仓库组件以 `main` 和必要的 `non-free-firmware` 为起点；
`contrib`/`non-free` 仅在明确的软件需求、许可证与分发审查后启用，
不因机器有 NVIDIA 显卡就默认切换专有驱动。

验证 Debian 仓库签名及软件包校验值，使用官方归档密钥体系；
不通过关闭签名验证、`trusted=yes` 或允许未认证包来绕过构建失败。
Backports 不是与稳定版相同程度的验收保证，必须走本项目回归。

## 4. 我们维护什么，不维护什么

| 层次 | 维护责任 |
|---|---|
| Debian 基础包 | 优先消费官方包及其安全修复，不另起一套通用发行版仓库 |
| 内核、固件、Mesa | 优先使用满足目标硬件需求的官方/指定 backports 包，记录版本并实机回归 |
| 不满足接口或约束的依赖 | 只为必要组件维护可复现的源码构建/包及最小补丁集 |
| PollyWM、PollyShell、PollyUI | 本项目主线维护，发行构建绑定明确源码提交 |
| 系统装配 | 本项目维护最小包清单、服务配置、启动介质、数据边界和验收流程 |

现有 wlroots 0.19.x（至少 0.19.3）、私有 patched SDL、Skia 及文本栈
不能直接假定与 Debian 仓库 ABI/构建选项一致。迁移时逐项核对：
优先用满足条件的发行包；否则固定源码版本、上游 URL、校验值和补丁，
生成可追踪的安装产物。准确版本以构建配方/锁定清单为准，不在多份文档中
维护互相漂移的“唯一正确版本”。

私有构建的库避免覆盖 Debian 系统库或破坏其它应用的 ABI。
每个自维护补丁记录原因、上游关联和删除条件；上游修复被采纳后应移除补丁。
**固定版本是为了复现，不是永不升级，更不是忽略安全修复的理由。**
对自行构建的组件，不能只等待 Debian 发出针对该二进制包的安全通知。

共享引擎/协议修复在同一主线完成，发行版差异限制在构建、打包和系统集成层。
不复制两套 PollyUI/PollyWM 业务代码分别维护。
开发候选可以取主线的明确提交；可交付版本使用不可混淆的版本号和提交清单，
不能从一个随时变化的分支名重建后仍声称是同一产物。

## 5. 上游同步节奏与发布流程

以下是维护计划，不代表已经创建自动化任务、授予推送权限或开放自动发布。

手动工具已补齐第一步：`desktop/tools/release-report.mjs` 离线检查并比较实际
运行包/启动镜像；`desktop/tools/check-debian-updates.sh` 在一次性 Debian
容器中刷新官方签名索引并输出固定渠道的候选差异，不在宿主机或用户系统安装更新。
运行包同时记录 `build-inputs.json` 的源码、配置和配方指纹。
这些是校验/发现工具，不等同于自动调度、安全公告判定、归档源留存或发布审批；
具体使用见 [Debian 构建说明](../desktop/release/debian/README.md)。

| 类别 | 计划节奏 |
|---|---|
| 安全公告 | 持续跟踪 Debian 和自维护依赖上游；影响当前功能的严重问题优先处理，不等月度批次 |
| 依赖更新候选 | 每周检查一次，汇总版本、修复、依赖和体积差异 |
| 常规试用镜像 | 以月度整理为起点；没有必要变更时不为日历强行升级 |
| 内核/Mesa/wlroots/SDL/Skia 等高风险更新 | 尽量分批，先验证再组合，保留可归因的对照 |
| Debian 下一大版本 | 单独建立迁移候选并重新验收；不随软件源别名自动跳转 |

统一流程：

1. 检查上游变更及适用性，形成更新范围，不直接改变已发布系统。
2. 更新版本锁定/构建输入，生成独立候选和差异报告。
3. 完成构建、运行、启动介质和数据兼容检查。
4. 对涉及驱动、图形、输入、网络、音频或启动链路的变化做目标实机回归。
5. 验收后才提升为新的可用基线，保留上一份已知可启动版本。

紧急安全修复可以缩短等待周期，但不能伪造或跳过必要的启动/基础功能验证。
候选失败就停止提升，记录失败及保留版本；不能用静默降级掩盖回归。
是否对外发布、生产签名和真实设备写入仍需要对应的具体授权。

## 6. 可复查的构建输入与产物

每次可交付构建至少记录：

- PollyUI 仓库提交、是否存在未提交修改、版本号及构建时间。
- Debian 代号、架构、软件源/组件、仓库元数据与实际安装包的精确版本。
- 自构建依赖的源码提交/归档校验值、补丁、构建选项和工具链版本。
- 内核、固件、Mesa、wlroots、SDL、Skia、字体和输入法数据版本。
- 运行文件清单、许可证/必要源码与补丁材料、SBOM、镜像校验和。
- 自动检查结果、实机反馈来源、已知限制和上一个可用版本。

构建与运行环境分离。复现发布版本使用留存的输入、官方快照或受控缓存；
更新候选从持续维护的软件源解析新版本。不能为了复现把所有用户永远锁在
一个不再包含安全修复的快照上。
仅记录版本号还不等于保证上游始终可下载；必须明确哪些输入已经留存。
运行环境二进制包已有显式留存工具 `desktop/tools/retain-debian-packages.py`：
精确匹配包版本和签名索引中的大小/校验值，保存在独立目录，不安装或执行。
`desktop/tools/test-offline-debian.sh` 在断网 minbase 容器中从这些本地 DEB
重建运行环境并验证普通用户健康检查及应用数据连续性。
该缓存不进入 Live，且不涵盖 bootstrap/SDK、Live 专属包或完整上游源代码；
不得把这项验证描述为完成所有输入留存或源码合规。
在达到并验证 bit-for-bit 重建前，只声称输入可追踪，不声称位级可复现。
校验和、官方 APT 包签名和本项目启动/更新镜像签名是不同的保证，不能混为一谈。
不把私钥、访问令牌或用户凭据加入源码、镜像或构建报告。

## 7. 验收、数据与回退边界

Debian 候选须覆盖普通/内存检查构建、核心及原生协议用例、安装后独立运行、
只读 UEFI 光盘/USB 启动，以及普通用户桌面、中文输入、剪贴板、
窗口/工作区/显示配置、网络与音频的基础闭环。
虚拟机和实机证据分开保存；CPU fallback 成功不算 GPU 加速通过。
不因底座迁移强制增加与首台机器基本使用无关的新功能。

之后的持久化/升级工作采用系统载荷与用户数据分离的方向：

### 程序与数据的更新契约

2026-10-07 用户明确希望借鉴 macOS/iOS 的程序与数据路径分离：
程序可以替换升级，用户数据不属于更新包的覆盖范围。
这项原则同时适用于持久化 Live 和完整 USB 安装，不能把它误解为
“只有 Live 才能分离数据”。完整安装也不要求把程序和数据混放。

| 内容 | 路径责任 | 更新行为 |
|---|---|---|
| 系统程序、私有库、随包资源 | 现有 `/usr/bin`、`/usr/lib/pollyui`、`/usr/share/pollyui`，以及后续受管理的应用包目录 | 按一致版本更新代码、库、JS 和资源；不存用户修改 |
| 应用配置 | `$XDG_CONFIG_HOME/pollyui/<app-id>` | 保留；必要时显式迁移格式 |
| 应用数据与 localStorage | `$XDG_DATA_HOME/pollyui/<app-id>` | 保留数据库和业务状态，不随程序覆盖或删除 |
| 缓存 | `$XDG_CACHE_HOME/pollyui/<app-id>` | 可以重建，不能保存唯一的数据副本 |
| 用户文档 | 用户选择的文档目录 | 不因升级或卸载应用而删除 |
| 临时状态 | `/run`、socket、PID、临时文件 | 不跨启动恢复 |

现有 Linux 运行时已提供 `application.configDir/dataDir/cacheDir` 和上述 XDG
命名空间；当前 Live 中这些目录仍在 RAM，尚不等于物理持久化。
正式应用必须由启动器提供稳定、显式的 `app-id`，不能包含安装路径或版本号。
未指定 ID 时按入口脚本真实路径生成命名空间的现有行为仅适合作为开发脚本隔离，
不能依赖它实现正式应用升级后的数据连续性。

更新应先暂存并校验完整程序版本，再切换入口；数据不在覆盖/清理范围内。
卸载默认保留数据，清除数据是独立的明确操作。数据格式迁移必须有版本、
独占访问与恢复策略；旧程序无法读取新格式时应拒绝不兼容回退或恢复对应数据副本，
不能静默创建空数据库伪装恢复成功。按应用分目录本身不等于 iOS 安全沙箱。

路径分离不必立即绑定具体分区方案；但任何更新流程都不能重刷承载用户数据的区域。
若采用完整 USB 安装，可进一步分开 EFI、系统/程序及用户数据区域。
包管理器数据库等系统状态应与对应程序版本一致，不能把整个 `/var` 当作可跨版本
共享的用户数据。实际分区、凭据持久保存、加密或真实介质写入仍需明确范围与授权。

### 应用包契约首阶段（C1/C2）

后续进展：C3/C4 的本地安装、注册及 Apps 入口已实现；显式替换/回退拒绝不兼容
数据格式。移除/恢复仅改变注册，保留代码缓存及 AppData，安全缓存回收和数据清除
仍待实现。下面保留契约层的设计说明，当前使用及完整边界见
[应用包管理](../desktop/APPLICATIONS.md)。

2026-10-07 开始实现共享应用包 schema 与数据定位规则，代码入口为
`desktop/shared/app-bundle.mjs`。安装态为一个包含 `manifest.json` 的应用目录，
对用户呈现为一个应用对象；后续 tar/zip 仅用于分发，解包验证和安装注册尚未实现。
当前接口只解析数据和生成启动计划，不自动执行应用、修改注册表或安装程序。

首版 manifest 示例：

```json
{
  "schemaVersion": 1,
  "id": "org.example.notes",
  "name": "Notes",
  "version": "1.0.0",
  "target": {
    "os": "linux",
    "architecture": "x86_64",
    "libc": "glibc"
  },
  "launch": {
    "kind": "pollyui",
    "entry": "main.mjs",
    "arguments": []
  },
  "data": {
    "layout": "pollyui",
    "schema": 1
  },
  "icon": "resources/icon.png"
}
```

`schemaVersion` 是包描述格式，`data.schema` 是应用声明的数据格式版本，两者独立。
`version` 使用数字主/次/修订版本及可选预发布后缀；修改显示名称、包位置、
程序版本或数据格式版本都不能自动改变数据目录。稳定 ID 使用小写点分标识，
后续由安装注册机制关联合法更新来源；**仅有同名 ID 不是可信发布者证明**。

包描述限制为 64 KiB，单参数最多 4096 字节、总参数最多 64 项；拒绝未知字段、
不支持的目标、无效 Unicode/NUL/控制字符，以及绝对路径、父目录跳转、
空路径段、反斜杠或 URL 形式的入口/图标。首版图标为包内 PNG/JPEG。
目标 libc 区分 glibc 与 musl，不能互换二进制；具体依赖是否可运行仍需安装校验。
这些词法检查不代替后续文件类型、符号链接、文件所有权及解包边界检查。

`launch.kind=pollyui` 使用宿主提供的 PollyUI 运行时路径，加显式 `--app-id`
和包内入口，继续使用现有 `XDG_*/pollyui/<app-id>` 数据路径，避免重复嵌套。
`launch.kind=native` 配合 `data.layout=xdg`，为支持 XDG 的第三方应用提供
按稳定 ID 分配的 config/data/cache/state 根目录；应用可以在各根目录下再建子目录。
启动计划不改写 `HOME`，不注入任意环境变量、不执行安装脚本、不隐含中间 shell。
需要特殊参数或不遵循 XDG 的第三方应用，必须后续明确适配，不能假装统一生效。
原生状态目录对应 `XDG_STATE_HOME`（默认 `~/.local/state`）；不据此新增或变更
现有 PollyUI `application` API。

数据目录不能与程序目录互为子目录，配置/数据/缓存/状态目录也不得相互覆盖。
每次启动计划固定具体程序版本目录和资源工作目录，不能依赖运行中会被升级切换的
模糊路径。已有进程版本保留、安装/卸载、签名来源、数据迁移与更新切换仍属于
C3–C8，尚不能仅凭生成计划就声称完成。
现有开发脚本的自动路径 ID 不变；通过此包规范启动的正式应用始终显式指定 ID。

验收使用真实 PollyUI 进程验证同一 ID 在 v1/v2、改名和路径搬迁后继续读取
同一份 localStorage，缓存清理不改业务数据；另用遵循 XDG 的子进程验证环境映射。
“不同用户”在此是逻辑 HOME/XDG 路径隔离测试，不是 OS 沙箱隔离或真实第三方应用
验收；Live 跨重启持久化、完整 USB 安装、受管理安装和数据格式迁移仍需后续实现。

### 持久化与恢复的实施要求

- 先用可丢弃虚拟磁盘验证，再使用用户指定的外部测试介质。
- 不自动探测并写入任意内盘；现有三块内置 SSD 的排除规则继续有效。
- 日常升级替换系统载荷，不以重刷整个启动盘的方式覆盖用户数据。
- 第一版采用手动升级和可选择的旧版本启动入口，不先建立在线自动升级服务。
- 数据格式变化必须有版本和兼容策略；不可逆迁移需要备份或明确拒绝旧版本。
  “系统能回退”不能掩盖“旧系统读不了已经迁移的数据”。
- 保留当前镜像的日志、校验和、上一份可用系统及必要的恢复说明。
- 不隐式增加密码/网络凭据的持久保存范围，也不把持久化描述为加密或安全存储。

Debian 的安全包同步先进入构建候选，不默认对正在运行的实机桌面执行无人值守的
大范围包升级。用户自行安装/升级系统包后，应记录相对基线的差异；
不能仍把这台机器描述为完全一致的已验收镜像。

## 8. 体积原则与实施顺序

选择 Debian 是为了 glibc 软件兼容与维护生态，不承诺它会自动比 Alpine 小。
应比较同功能、同驱动范围的启动镜像，而不是拿裸 `minbase`/`slim` 容器
与带完整固件、图形栈、字体和输入法的 Live ISO 比较。

分别记录镜像压缩大小、安装态各项占用、启动时间及运行内存。
根据实机结果裁剪无关固件、字体、词库与诊断组件；先确认依赖再裁剪，
不简单删除 Mesa 正在链接的 LLVM，也不先移除可靠回退路径。
没有完成同功能测量前，不给出未经验证的 100/200 MB 镜像承诺。

实施顺序：构建输入清单和最小 rootfs → Debian/glibc 编译与基础回归 →
等功能 Live/USB 镜像 → 同一实体机验收并建立 Debian 基线 →
可选持久化 → 保留数据的手动升级/回退 → 基于实测的体积和性能优化。

本次只记录原则与计划，不迁移当前镜像、不安装宿主机软件、不创建定时同步，
也不自动推送、发布或写入启动盘。
