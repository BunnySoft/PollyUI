## 首次发版目标：实体机基础功能验证

用户最新明确：首次发版不是完成大而全的桌面发行版，而是把已有的
PollyWM / PollyUI 基础功能放到指定实体机上，证明实际工作正常。
下面的历史调查和长期路线图不能自动变成首发门槛。

- 在指定 x86_64 UEFI 实体机上从启动介质进入普通用户桌面；不依赖
  GNOME/KDE，不修改内置磁盘，保留内存型 Live。
- 验证真实 GPU/显示链路、键盘鼠标、分辨率/缩放，以及原生应用启动、
  窗口操作、焦点、手动工作区和主题切换。
- 验证字体、中文输入、复制粘贴，以及目标机器上已经实现的网络和音频功能。
- 重复启动和基础操作能够复现；错误有可导出的本地诊断记录，逐项记录
  实机通过/失败，不能用 WSLg 或虚拟机结果替代。
- 文件管理器、完整 Portal/录屏、完整无障碍、高级效果、Xwayland、
  安装器、签名更新和其它平台保留为后续工作，不阻塞这次实体机预览版。
- 电源授权继续暂缓；无密码 Live 的密码锁和挂起/休眠继续默认禁用。

## 当前主题进展

- Shell JS 负责读取 JSON、校验、合并有限用户覆盖和消费界面参数。
- 原生窗口装饰接收受限的准备/提交请求；配置副本跟随各窗口的 configure 生命周期。
- 大主题文档通过封存的内存描述符传递，避免 Wayland 单消息容量限制。
- 本地位图、同名配置重载、失败保留、恢复内建主题和应用只读订阅已接通。
- 面板、Dock、菜单、托盘、通知及系统设置接入布局/字体参数；壁纸图层不再由预设分支写死。
- 原生标题栏的按钮、字体、对齐、条纹和悬停参数来自配置。任意桌面模板、自动监听以及新阴影/模糊能力不属于此阶段。

## 结论

完全数据驱动的主题不是被 Wayland、wlroots 或 PollyUI 禁止了。当前实现解决的是“五个可靠的内建预设”，并没有实现“外置主题配置协议”。

仅把 `themes.mjs` 改名为 JSON 文件不能完成目标：配置还必须贯穿加载、校验、渲染、合成器通信、窗口几何提交和应用组件。主要障碍是这些接口尚未建立，而不是需要替换现有渲染引擎。

## 调查基线

以下证据及行号对应改造前的 `08a5b9c`，作为架构取舍的历史依据；不是当前代码状态。

| 层面 | 当前事实 | 配置化还缺什么 |
|---|---|---|
| 主题注册与加载 | `desktop\shell\themes.mjs:12-147` 导出冻结的五项数组；`getDesktopTheme()` 只查内建 ID | 外部文件发现、版本化 schema、字段/资源边界校验、加载错误和安全默认主题 |
| 原生数据来源 | `desktop\tools\generate-decoration-themes.mjs` 将部分 JS token 生成 C 数组 | 运行时主题快照，不能继续仅靠编译时头文件 |
| Native bridge | `src\desktop\windows.c:583-600` 再次按生成的 C 表检查主题 ID | 接受经过校验的新配置，而不是只能选择已编译 ID |
| 私有协议与合成器 | `desktop\protocols\polly-appearance-v1.xml` 只传 ID；`desktop\compositor\decoration.c:510-527` 再查静态表 | 有版本、容量上限、接受/拒绝结果的主题提交机制，仍仅向可信 Shell 开放 |
| 真实装饰渲染 | `decoration.c:117-136,294-353` 中按钮尺寸/间距、黄绿按钮、条纹混色、hover 混色、文字留白和字形笔画有固定值 | 把可主题化的细节完整提取为 token；绘制和命中测试使用同一份尺寸 |
| 壁纸与 Shell 布局 | `desktop\shell\appearance.mjs:54-98` 写有图案位置和部分颜色；`shell.mjs:142-156` 固定菜单栏高度、Dock 宽度公式和边距 | 壁纸图层/资源参数，以及有边界的面板/Dock 布局参数 |
| 预览与真实效果 | `appearance.mjs:100-161` 有预览专用逻辑；生成器不输出 `shadow`、`controlRadius`、`unifiedToolbar` 等全部字段 | 明确每个字段的消费者与支持范围；不能以预览画出了效果作为真实合成器已实现的证据 |
| 应用组件 | `js\naive.mjs:14-31,1425-1430` 有独立的 light/dark 主题；演示应用也有自己设置的样式 | 独立应用进程的主题订阅、语义 token 映射和应用自行覆盖规则 |

另外，当前 `shell.mjs:190-257` 按 ID 避免重复提交。即使未来重新加载了同名配置，也必须引入配置修订号，否则合成器可能不会收到更新。

辅助界面还有一个需要纳入后续覆盖的静态代码缺口：音频、网络、通知等主要在自身数据变化时调用 `paint()`；主题切换入口没有统一广播到所有这些已打开的界面。需要补充专门场景确认和统一刷新契约，而不能仅验证壁纸/任务栏换色。

## 必须保留的边界

- 配置负责外观，窗口关闭、焦点、工作区、认证和权限等行为仍由代码负责。
- 主题文件应是受限数据，不是以可信 Shell 权限执行的第三方 JavaScript。
- 保留 PollyWM 的 C 实现边界，不为读主题把 QuickJS、Skia 或整个 PollyUI 引入合成器。
- 改变标题栏高度和边框不只是重画：必须与 xdg configure/ack/commit、窗口命中区域及 pending/current 几何一致。
- 运行时替换主题时，旧窗口仍可能引用旧配置；要有明确的快照生命周期，而不是直接覆写全局数据。
- 无效配置、丢失资源、超限尺寸或不支持的效果应明确报错，保留最后可用主题，不让整个 Shell 被协议错误断开。
- 当前未实现的背景模糊、真实合成器阴影等效果，仍需先实现对应能力；增加一个配置字段不会自动带来这些能力。
- 不能承诺强制重绘任意第三方应用自己的客户端装饰和控件。

## 主题部分采用的取舍

用户要求依次实施后，按下列推荐边界落实首阶段主题机制。

| 编号 | 需要确认的范围 | 建议 |
|---|---|---|
| T1 | 第一阶段覆盖到哪里 | 先覆盖 Shell、真实窗口装饰和系统设置；PollyUI 应用组件通过显式 opt-in 接入，第三方应用保持自身风格 |
| T2 | 配置和资源形式 | 版本化 JSON + 本地位图资源；不支持可执行脚本、远程资源和任意文件路径 |
| T3 | 布局自由度 | 先完整开放已有布局的颜色、尺寸、字体、状态、间距和按钮样式；任意重排整个桌面的模板语言另立范围 |
| T4 | 应用更新方式 | 先显式“应用/恢复”与事务式失败回退；文件监听热更新以后再加 |
| T5 | 继承与覆盖 | 系统默认主题 + 有限用户覆盖；明确合并规则，避免一开始支持复杂的多层继承和条件语言 |

若上述边界获认可，建议实施顺序为：梳理字段及消费者 → 定义和验证 schema → 迁移现有主题数据 → 增加受限原生提交与快照生命周期 → 统一界面刷新 → 应用 opt-in → 效果一致性与坏配置回退覆盖。
